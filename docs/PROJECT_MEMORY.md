Документ для продолжения работы в новых сессиях: что за проект, какие решения приняты и почему, что проверено,
что известно об ограничениях и что планируется. Обновляй его, когда принимаешь новое решение или закрываешь этап.

## 1. Задача и заказчик

- Заказчик — владелец сети клиник лазерной хирургии вен «Варикоза нет», первая клиника — Владивосток
  (ул. Лазо, 6Б; местное время UTC+10, аккаунт Mango — по Москве, разница 7 часов).
- Администраторы звонят пациентам и принимают звонки по регламенту. Раньше звонки оценивались вручную по
  Excel-форме (отсюда шаблон чек-листа). Нужен сервис: записи звонков → оценка по регламенту → балл и
  обратная связь администратору.
- Условия заказчика:
  - максимально бюджетно;
  - телефония — Mango Office;
  - сейчас одна клиника и 2 администратора, в перспективе сеть до ~70 клиник и колл-центры;
  - сервис работает на компьютере в клинике (Windows);
  - персональные данные заказчик считает не критичными;
  - ИИ — через OpenRouter;
  - балл — взвешенный по значимости пунктов (веса можно менять);
  - пункты, которые нельзя проверить по записи, исключаются из оценки;
  - критерии должны гибко настраиваться в интерфейсе каждой клиникой;
  - звонки должны подтягиваться из Mango автоматически для каждой клиники или колл-центра.
- Порядок работы, который задал заказчик: предложить варианты → обсудить → разрабатывать. Общение — по-русски.

## 2. Ответы заказчика по правилам оценки

Внесены в подсказки пунктов шаблона `config/checklists.yaml` (в правила промпта `app/evaluation.py` не вносились):

1. Полное название клиники называть не обязательно — краткое засчитывается.
2. Первичный или повторный пациент — можно понять из разговора без прямого вопроса.
3. Цель исходящего звонка можно назвать в любой момент разговора, не обязательно в начале.
4. «Окошки», «минутку», «венки» и подобные — считаются уменьшительно-ласкательными (нарушение).
5. Слова-паразиты — нарушение только если их 3 и больше.
6. Цена «выигрыша» или «подарка» не засчитывается: должна прозвучать «стоимость по акции».
7. Настройки должны быть гибкими (редактор критериев), звонки — из Mango автоматически.

Где именно: ответ 1 — только в подсказке IN04 (входящий звонок), ответ 3 — только в RQ07 (исходящий по заявке),
ответы 4–6 — в G14, G13 и пунктах о стоимости (IN16, RQ19, ON16). **Не сделано:** в исходящих сценариях
(RQ05, ON05, RM05, RS04, NS04 — представление; ON07, RS07 — цель звонка) этих подсказок нет. Добавлять через
редактор критериев работающей клиники: правка шаблона до неё не дойдёт (см. `docs/ARCHITECTURE.md`).

## 3. Ключевые решения

**Расшифровка.** Сравнивались Whisper, GigaAM и T-one на реальных записях Mango. Выбран GigaAM v2 (RNNT,
sherpa-onnx): лучше на русской телефонной речи, работает на процессоре, бесплатно. Модели (~270 МБ) скачиваются
с github.com при первой расшифровке. Mango пишет моно — голоса администратора и пациента разделяются по паузам
(Silero VAD) и «отпечаткам голоса» (TitaNet), роли определяются по словам («клиника», «Варикоза нет»,
«администратор»); если по словам не получилось, кто администратор, указывает ИИ при классификации. Стерео-записи (если появятся) делятся по каналам.

**Оценка ИИ.** Два шага: классификация (тип звонка, имя и голос администратора) и оценка по пунктам чек-листа
(«да / нет / не применимо» с цитатой, сильные стороны, зоны роста с рекомендацией и примером фразы).
Фильтры согласованности: сильная сторона не может хвалить невыполненный пункт, зона роста — только по пункту «нет».
Модели (OpenRouter):

| Назначение | Модель | Стоимость звонка 3–6 мин |
|---|---|---|
| Тип звонка (`LLM_CLASSIFY_MODEL`) | Claude Haiku 5.5 | входит в оценку |
| Оценка по умолчанию (`LLM_MODEL`) | Claude Haiku 5.5 | ≈ 0,3 ₽ |
| Кнопка «Переоценить точной моделью» (`LLM_PRECISE_MODEL`) | Claude Sonnet 5.5 | ≈ 4–6 ₽ |

**Балл.** Взвешенный процент: «да» приносит баллы значимости (высокая 3, средняя 2, низкая 1), «нет» — 0,
«не применимо» не учитывается. Отдельно — общие правила, сценарий и итог.

**Сеть клиник.** Клиники, сценарии и пункты чек-листа хранятся в базе; у каждой клиники свой чек-лист, сведения
для ИИ, часовой пояс, ключи Mango. Роли: администратор сети (все клиники) и руководитель клиники (только своя).

## 5. Mango Office (сверено с документацией API ВАТС v1.8/v1.10 и рабочими интеграциями)

- Адрес `https://app.mango-office.ru/vpbx/`; POST-форма `vpbx_api_key`, `sign`, `json`;
  `sign = sha256(vpbx_api_key + json + vpbx_api_salt)` (не HMAC).
- Статистика: `stats/request` (`date_from`/`date_to` — обычный Unix, период ≤ 1 месяца) → `key` →
  `stats/result` (204 — ещё готовится, 404 — ключ устарел, 200 — CSV через «;» без заголовка, колонки в
  порядке `fields`, строки через `\r\n`). Поле `records` — `[id1,id2]`, иногда без скобок.
- Направление: только `from_extension` — исходящий, только `to_extension` — входящий, оба — внутренний;
  сотрудники бывают SIP-адресами `sip:login@domain.mangosip.ru`.
- Запись: `queries/recording/post` с `action=download` → 302 на одноразовую ссылку files.mango-office.ru.
  Записи должны храниться в «Облачном хранилище» ЛК; удалённые там через API не скачать.
- Лимиты: `stats/request` 1 раз в 2 с на АТС, `stats/result` не чаще раза в 5 с, при превышении — 429.
  Неверные запросы могут заблокировать API на ~2 минуты. Фильтр IP в API-коннекторе блокирует компьютер с
  меняющимся адресом.
- Ключи: ЛК Mango → «Интеграции» → «API Коннектор» («Уникальный код АТС» и «Ключ для создания подписи»).

## 7. Известные ограничения

- Копирование чек-листов туда-обратно может переставить пункты, если у нескольких разных сценариев одной
  клиники одинаковые названия (редкий искусственный случай; в случайных прогонах 2 из 120).
- Если базу больше 30 с держит другая программа (например, открытый редактор базы), запуск не пройдёт: на новой
  базе не запишется стандартный чек-лист, на существующей — возврат прерванных звонков в очередь
  (`requeue_interrupted`) или добавление новых колонок. Откладывается только перестройка таблицы звонков
  (ждёт не дольше 5 с).
- Сервис рассчитан на один процесс (второй запуск с той же папкой `data\` не стартует): ключ подписи сообщений,
  счётчик попыток входа и очередь обработки живут в одном процессе. Для нескольких процессов или серверов их нужно
  вынести в базу, а «брошенные» звонки определять по времени, а не по свободному обработчику.
- Зависшую внутри расшифровки (в коде sherpa-onnx) обработку сервис прервать не может — помогает перезапуск.
- SQLite достаточно для одной клиники; для десятков клиник — сервер и, возможно, PostgreSQL.
- Данные — в папке `data/`: база `ocenka.db` (режим WAL, рядом файлы `-wal`/`-shm`), записи `audio/`, модели
  `models/`, ключ сессий `secret.key`. Автоматической резервной копии пока нет; простое копирование `ocenka.db`
  при работающем сервисе может потерять свежие данные (нужен `sqlite3` backup или остановленный сервис).

## 9. Как обновление доходит до заказчика (Windows)

- Заказчик ставит сервис через GitHub «Code → Download ZIP» в папку вроде `C:\ocenka`. Git у него нет.
- Ветка `claude/charming-meitner-vvli1z` — единственная в репозитории и ветка по умолчанию на GitHub, поэтому ZIP
  собирается из неё. Изменения в другой ветке до заказчика не дойдут, пока их не перенесут сюда.
- При обновлении сохранить `data\` (база, записи, модели, `secret.key`) и `.env`: их нет в репозитории.
- `start.bat` при каждом запуске ставит зависимости из `requirements.txt`; миграции базы выполняются при старте.
- `.env` копируется из `.env.example` только если его ещё нет: новые переменные у заказчика сами не появятся,
  действуют значения по умолчанию из `Settings`. Настройки, которые клиника меняет сама (например, будущий
  Telegram-бот), лучше хранить в базе и править в интерфейсе — как ключи Mango.
